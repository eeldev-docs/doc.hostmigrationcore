Features

What gets saved

Which objects​

ObjectNeeds a Host Migration Id?
Placed actorsYes
Actors spawned at runtimeYes. They are spawned again on the new host.
Player pawnsYes
PlayerStatesNo. Matched to the returning player by unique net id.
GameState, GameModeNo
ComponentsNo. Saved with their owner.

A placed actor that was destroyed before the migration stays destroyed on the new host.

Which data​

  • SaveGame variables. Tick SaveGame on Blueprint variables (Advanced section), or use UPROPERTY(SaveGame) in C++. Structs, arrays, maps and object references are supported. For structs, see below.
  • Custom data (C++). Implement IHostMigratable for anything SaveGame cannot express.
  • The actor's transform is always saved.

Components​

Every component with SaveGame variables (or IHostMigratable) is saved with its owner: default components, components added in the Blueprint editor and components added at runtime. This works on actors, PlayerStates, the GameState and the GameMode alike, so an inventory component on the PlayerState just works.

Components are matched by name. A component that was added at runtime and is missing on the new host is created again with the same name and class.

Structs​

Every struct member needs SaveGame too

Marking a struct variable (or an array of structs) as SaveGame is not enough. Inside the struct, only members that are also marked SaveGame are saved; the others come back with their default values. This applies at every level, also to structs inside structs.

  • Blueprint structs: open the struct and tick SaveGame on each member that should carry over.
  • C++ structs: add SaveGame to each member's UPROPERTY.

Example: an inventory component with a SaveGame array of items.

USTRUCT(BlueprintType)
struct FInventoryItem
{
	GENERATED_BODY()

	UPROPERTY(SaveGame, BlueprintReadWrite)
	FName ItemId;              // saved

	UPROPERTY(SaveGame, BlueprintReadWrite)
	int32 Count = 0;           // saved

	UPROPERTY(BlueprintReadWrite)
	int32 Durability = 0;      // NOT saved: 0 after a migration
};

UCLASS()
class UInventoryComponent : public UActorComponent
{
	GENERATED_BODY()

	UPROPERTY(SaveGame)
	TArray<FInventoryItem> Items;
};

After a migration Items has the same entries with the same ItemId and Count, and Durability is 0.

Items as UObjects​

Items created as objects (NewObject<UInventoryItem>(this), or Blueprint "Construct Object") are not saved: a reference to them points at an object that does not exist on the new host, so it is null after the migration. Use structs for item data, or in C++ save the items yourself with IHostMigratable.

References​

Object references are stored so they still point at the right thing after the migration:

Reference toStored asAfter the migration
An actor with a Host Migration Id, or one of its componentsMigration idPoints at the same actor, even if it was spawned again.
A PlayerStateUnique net idResolves if that player is connected when the object is loaded. Otherwise null.
Assets, classes, placed actors without an idPathAs before.

Raw pointers, TObjectPtr, TWeakObjectPtr and references written through IHostMigratable all work.

What is not saved​

  • Variables without the SaveGame flag, including struct members without it.
  • Objects created at runtime that are not actors or components (NewObject, "Construct Object").
  • Actors without a Host Migration Id.
  • Timers, animation state, physics velocity, in-flight RPCs. Save what you need in On Host Migration Save and restart it in On Host Migration Restored.
  • Progress made after the last snapshot (at most one Snapshot Interval). A graceful leave sends a final snapshot.
